## 版本一：标准版（推荐，占 12~16 行）

**悦集商城 · B2C 电商交易平台**　｜　独立开发 / 技术负责人　｜　2025.09 – 2026.11

**技术栈**：Java 21 / Spring Boot 3.2.5 / Spring Cloud 2023（Gateway·OpenFeign）/ MyBatis-Plus / MySQL 8 / Redis / Vue2 + Element UI / Vue3 + Vant4 / Docker

**项目描述**：面向 C 端消费者与商家的多端电商平台，覆盖商品、订单、支付、售后、营销、会员、商户入驻全链路。后端 13 个 Maven 模块、10 个微服务进程，三端前端（平台后台 / PC 商城 / H5），单库 75 张表，历经 11 个版本迭代。

**核心工作与成果**：
- **微服务架构落地**：按业务域拆分网关 + 9 个业务服务，自研 `mall-common` 契约层（统一响应体、鉴权过滤器、全局异常、Feign 契约），跨域调用全部走 Feign 接口而非跨库 JOIN；**刻意选择「拆服务不拆库」**，把拆错边界的代价控制在改包结构级别，避免中小规模系统陷入分布式事务泥潭。
- **三方身份鉴权体系**：设计平台运营 / C 端会员 / 商家三套独立令牌（商家走 `Merchant-Token` 请求头），支持同浏览器并行登录两套后台；网关层做令牌透传与路由级拦截，下游统一上下文注入，越权访问全程留痕。
- **交易一致性保障**：订单 / 售后全流程采用状态机 + 条件 UPDATE（`WHERE id=? AND status=?`）实现幂等流转，把并发判据交给数据库行锁，杜绝支付回调重复触发导致的状态错乱；库存扣减失败通过显式补偿回滚，不依赖全局事务。
- **外部依赖 SPI 化**：支付渠道、物流轨迹、短信/站内信、工作流引擎均抽象为「接口 + 多实现 + 配置开关」，无真实渠道的环境可跑通完整链路，**无渠道时明确返回 503 而非伪造成功**，保证测试环境与生产语义一致。
- **质量体系从 0 到 1**：搭建三层验证链路——201 例单元/契约测试（状态机、越权隔离、Feign 契约）→ 78 条接口冒烟（**刻意走 devServer 代理而非直连服务，能暴露网关路由与代理配置问题**）→ 199 条 CDP 浏览器断言（真实 Chrome 收集 console 异常、失败请求、白屏、破图）；收敛为一条命令，退出码分级（0 通过 / 1 断言失败 / 2 环境不满足），可直接接入 CI。
- **研发效率工具**：编写全页面诊断脚本，注入登录态后自动遍历 33 个页面并输出结构化报告（错误 / 异常 / 失败请求 / 截图），把人工半小时的回归压缩到 90 秒，一次性定位并修复「列表恒空」「表格渲染崩溃」等 5 类隐蔽缺陷。

**技术难点与解决**：
- **商家域全链路 401**：单测全绿但商家后台整体不可用。定位为网关鉴权过滤器只识别 `Authorization`，第二套令牌在网关即被拦截，下游写好的分支永远走不到。修正为「商家域透传 + 下游鉴权」，并补上经网关的真实链路用例——**核心认知：绕过网关的鉴权测试等于没测鉴权**。
- **跨端契约漂移**：新模块手写分页返回 `list`，而全局契约是 `records`，前端取数永远为空且空表时不报错，极难发现。统一分页契约并加入前端类型防御，同时在测试中固化字段名断言。
- **雪花 ID 精度丢失**：19 位 `Long` 主键经 JS 序列化后被截断，所有按 ID 的查询「记录不存在」。通过全局 Jackson 序列化为字符串解决，并单独处理 Map 内数值（不受全局配置管辖）的遗漏场景。

## 版本三：架构侧重版（面中高级 / 架构岗，突出决策与权衡）

**悦集商城 · 电商交易平台**｜技术负责人｜Java 21 · Spring Cloud · MySQL · Vue

负责整体架构设计与技术选型，主导 11 个版本演进，核心决策如下：

| 决策 | 取舍理由 | 结果 |
|---|---|---|
| 按业务域拆服务，但**不拆库** | 微服务收益在变更隔离而非物理分库；单库让「拆错边界」的代价可控 | 跨域一致性靠本地事务 + 显式补偿，无全局事务依赖 |
| `mall-common` **只放契约不放业务** | 公共库承载业务会形成隐式耦合，任何改动引发全量重编译与版本漂移 | 契约稳定，服务可独立升级 |
| 业务异常**统一 HTTP 200 + body code** | 前端拦截器只需处理一种响应形态 | 代价是测试必须断言 code 而非状态码，为此封装断言辅助方法 |
| 状态流转一律**条件 UPDATE** | 「先查再改」在并发下有判据窗口 | 重复回调天然幂等，无需分布式锁 |
| 外部依赖全部 **SPI 化** | 测试环境不应依赖真实渠道 | 无渠道明确 503，绝不伪造成功 |
| 新能力**用新模块隔离** | 并行开发时新模块编译失败不阻塞主链路 | 出问题可单独下线 |

质量上建立「单测 → 接口冒烟 → 浏览器走查」三层验证与 DDL 幂等纪律（迁移脚本连跑两遍 exit=0 才算通过），把「单测全绿但端到端不通」作为最高危信号优先排查测试路径。

## 面试时的展开素材（不进简历，用于被追问）

**问：为什么不全拆库？**
拆库换来的是分布式事务、跨库查询、数据同步三件麻烦事，而收益（变更隔离）在单库 + 逻辑归属下已经拿到。这个项目的服务边界还没有稳定到值得付这个代价——真拆错了，改包结构只要一天，迁数据要一个月。

**问：幂等怎么做的？**
不靠 Redis 锁，靠数据库：`UPDATE ... WHERE id=? AND status=?`，影响行数为 0 就是重复请求，直接返回成功。售后七态、订单多态全部这套。支付回调天然重复，这里必须幂等。

**问：测试怎么保证真的有效？**
三层递进。最关键的一条是冒烟脚本走 devServer 代理而不是直连服务——因为踩过一次「单测全绿但商家后台完全不可用」，根因是鉴权在网关层，而单测直打服务端口绕过了网关。测试路径和用户路径不一致，测试就是安慰剂。

**问：最难查的 bug？**
分页字段名 `list` vs `records`。它不报错——空表时页面只是空着，看起来像「还没数据」。最后是靠写全页面诊断脚本、造了数据之后才暴露。教训是：契约类错误在无数据时测不出来，必须造数据再验。

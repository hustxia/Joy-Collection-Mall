# 悦集商城 · 项目经验总结

> 一份写给「下一个接手的人」的复盘：架构为什么这么定、坑踩在哪、哪些做法值得照搬。
> 覆盖 V3 → V14 共 11 个版本、12 个后端模块、3 端前端、75 张表。

## 一、项目全貌

| 维度 | 实际情况 |
|---|---|
| 后端 | Spring Boot 3.2.5 / Spring Cloud 2023.0.3 / Java 21，Maven reactor 13 模块 |
| 服务 | 运行 10 个进程：网关 8080 + 9 个业务服务（8201~8209）；另有公共库 / 配置 / 测试支撑 3 个非运行模块 |
| 前端 | 三端独立工程：后台 `mall-web` 9431（Vue2 + Element UI）、PC `mall-pc` 9432（Vue2）、H5 `mall-shop` 9531（Vue3 + Vant4） |
| 数据库 | MySQL 8 单库 `yueji_mall`，75 张表（40+ 张 `mall_*` 业务表） |
| 测试 | `mvn -o test` 201 例全绿；接口冒烟 78 条；浏览器走查 199 条断言 |
| 演进 | V3 主链路 → V4 售后闭环 → V5 微服务化 → V6 生产就绪 → V7 C 端玩法 → V8 秒杀拼团抽奖 → V9 分销 → V10 商户入驻 → V12 交易真实化 → V14 能力补齐 |

**一句话结论**：这个项目真正的价值不在功能数量，而在于它把「电商交易系统最容易出错的地方」（状态机、金额、库存、鉴权边界、跨端契约）全部踩了一遍，并且每个坑都留下了可检索的代码级记录。

## 二、架构决策与理由

### 1. 按业务域拆服务，但数据库不拆（单库 + 逻辑归属）

拆的是**代码边界和团队边界**，不是物理数据库。每个服务只写自己域内的表，跨域一律走 Feign 契约，不跨库 JOIN。

**为什么对**：微服务的收益来自「变更隔离」，不是「物理分库」。演示/中小规模项目强行分库，只会换来分布式事务和跨库查询的灾难。单库让「拆错边界」的代价降到最低——真要合并，改包结构就行，不用迁数据。

**代价**：跨域一致性靠本地事务 + 显式补偿（如扣库存 Feign 失败要回滚订单），没有全局事务兜底。

### 2. `mall-common` 只放契约，不放业务

`Result` / 鉴权过滤器 / 全局异常 / 分页配置 / Feign 契约与 DTO 在这里，任何业务逻辑都不许进来。

**踩过的雷**：改了 `mall-common` 忘记 `mvn install`，各服务跑的还是 `.m2` 里的旧 jar，现象是「代码明明改了、跑起来没变化」。这是微服务多模块最典型的幽灵问题（坑库 `spring-boot-3.md` #3）。

### 3. 三方令牌分流：平台 / 会员 / 商家，互不通用

| 身份 | 令牌载体 | 校验位置 |
|---|---|---|
| 平台运营 | `Authorization: Bearer` | 网关 `GatewayAuthFilter` → 下游 `AuthContextFilter` 双校验 |
| C 端会员 | `Authorization: Bearer`（不同签发域） | 下游 `AuthContextFilter` |
| 商家后台 | **`Merchant-Token`** | 网关**透传**，下游 `AuthContextFilter` 商家分支 |

**为什么商家单独一个头**：商家账号是独立账号体系（`mall_merchant_user`），与平台 `sys_user` 隔离；同一个浏览器可能同时开平台后台和商家后台，共用一个头会互相顶掉会话。

**这次踩的坑**：网关白名单只放平台匿名接口，商家域整个被「无 Bearer → 401」拦死。**加一种令牌 = 网关和下游两处都要改**，只改下游等于没改（详见 §三-B1）。

### 4. 业务异常走 Result 包装：HTTP 200 + body code

`{code:403, msg:"越权"}` 而不是 HTTP 403。

**好处**：前端拦截器只处理一种响应形态，不用区分「HTTP 层错误」和「业务层错误」。

**代价（必须记住）**：所有测试断言不能用 `status().isForbidden()`，要断言 body 的 `code` 字段。这个项目为此专门写了 `bizError(res, 403)` 断言辅助——**否则测试会全绿但功能全坏**（坑库 `spring-boot-3.md` #11）。

### 5. 状态机 + 条件 UPDATE 幂等

售后七态、订单多态，所有状态流转都是：

```sql
UPDATE mall_refund SET status = #{to}
WHERE id = #{id} AND status = #{from}   -- 条件更新，影响行数 0 就是幂等返回
```

**为什么不用「先查再改」**：并发下「查到旧状态 → 判断 → 更新」中间有窗口，重复回调会把状态推错。条件 UPDATE 把判据交给数据库的行锁。

### 6. 外部依赖全部 SPI 化

`PayChannel`（sandbox / wxpay / alipay）、物流轨迹、消息通道（短信 / 站内信）、工作流引擎（builtin / activiti）都是接口 + 多实现 + 配置开关。

**好处**：没有真渠道、没有 Redis、没有 Activiti 的环境一样能跑完整链路；接真渠道只加实现类。**没有渠道配置时明确报 503，绝不伪造支付成功**——这条纪律比任何功能都重要。

### 7. 新能力用新模块隔离，不往老模块塞

V14 的客服工单（`mall-support` 8208）、消息触达（`mall-message` 8209）都是独立新模块，通过 Feign 只读调用老服务。

**为什么**：并行开发时新模块的编译失败不会阻塞主链路；出问题可以单独下线。

## 三、踩过的坑（按类型，每条都有代码级根因）

### A. 契约类 —— 最贵的一类，因为「单测全绿、功能全坏」

**A1. 手写分页字段名偏离全局契约（`list` vs `records`）**

新模块手写 `data.put("list", records)`，而 MyBatis-Plus `IPage` 和其他所有模块都是 `records`。前端 `d.records` 取不到：

```js
// ❌ 这行是反模式：把「类型错误」变成「运行时崩溃」
this.templates = d.records || d || []     // d 是对象 → 整个 Map 塞进 el-table → data.indexOf is not a function

// ✅ 显式分支，宁可空也不崩
this.templates = Array.isArray(d) ? d : (d.records || [])
```

**隐蔽点**：无数据时页面不报错、只是空列表，看起来像「还没数据」，实际是取数永远失败。

**A2. 19 位雪花 ID 被 JS 截断**

后端 `Long` 直接序列化，前端 `Number` 精度只到 2^53 → `2112438959048089602` 变成 `...089000`，所有按 ID 的请求「记录不存在」。

**修法**：全局 Jackson 配置把 `Long` 序列化成 String。**注意 Map 里的 Long 不受全局配置管辖**，要手动 `String.valueOf()`（坑库 `spring-boot-3.md` #57）。

**A3. 异常返回 HTTP 200**

见 §二-4。测试断言状态码 = 假通过。

### B. 鉴权类 —— 都是「以为通了其实没通」

**B1. 网关只认 `Authorization`，第二套令牌被一刀切 401**（本次修复）

```java
// ❌ 商家请求没有 Authorization 头 → 网关直接 401，下游写好的商家分支永远走不到
if (isWhitelisted(method, path)) return chain.filter(exchange);
String authorization = request.getHeaders().getFirst(HttpHeaders.AUTHORIZATION);

// ✅ 商家域只透传，鉴权交给下游 AuthContextFilter
private static final String MERCHANT_ADMIN_PREFIX = "/merchant-admin";
if (isMerchantAdminPath(path)) return chain.filter(exchange);
```

**为什么单测没发现**：`MerchantIsolationTest` 直打 8207 不过网关。**结论：只测服务、不测网关的鉴权测试，等于没测鉴权。**

**B2. 静态资源 401**：文件映射做了、`AuthContextFilter` 白名单没加 → 图片接口 200 但图片全破。

**B3. ThreadLocal 只 set 了 username**：审计字段 `create_by` 永远 null，静默无痕。

### C. 数据类

**C1. 逻辑删除列进唯一索引**：第二次删除同一业务键必撞 `Duplicate entry`。唯一索引要带 `deleted`，或改成软删除标记 + 业务唯一键重新设计。

**C2. 手写 INSERT 列名与表结构不符，被 catch 吞成「静默无痕」**

越权留痕写了 `sys_oper_log.oper_time`（表里没有这列）→ 异常被 `catch(Exception e){ log.warn }` 吞掉 → **留痕从未成功过，但功能看起来正常**。

**教训**：`catch` 里只 `log.warn` 的分支，等于「这个功能可能从来没跑过」。要么让异常冒泡，要么在测试里断言副作用真的发生了。

**C3. 脱敏占位符炸穿列宽**：`"cancelled_" + 19位ID` = 29 字符，`phone varchar(20)` → 注销 500。占位符长度必须按目标列宽设计。

**C4. 运行库只跑到旧版本迁移**：代码用了新列，库没 ALTER → `Unknown column`。DDL 脚本必须幂等且每次启动前校验（本项目三个脚本各跑两遍 exit=0 才算过）。

### D. 前端类

**D1. Layout 静态 import 路由表 → 循环依赖白屏**：加载顺序不利时 `Layout === undefined`，所有页面白屏且无明显报错。

**D2. 菜单从路由推导，混入独立布局**：`/merchant`、`/merchant/login` 被当成菜单项渲染出假入口。**顶层路由 ≠ 菜单节点**，独立布局要按前缀排除。

**D3. Vue2 模板用了 import 的函数但没挂 `methods`**：整张表格渲染中断（`_vm.thumb is not a function`）。

**D4. Vant4 lazy-load 不注册插件**：图片全破图，无 404、无报错。

**D5. vite 代理漏静态前缀**：`/img` 没代理 → vite 拿 `index.html` 兜底返回 200 text/html → 页面不报 404 但全是破图，极易误判为数据问题。

### E. 环境类（Windows 特有，占比不低）

| 现象 | 根因 | 修法 |
|---|---|---|
| 服务起在随机端口 | 环境变量 `SERVER_PORT` 空串覆盖 | jar 启动必须显式 `--server.port` |
| 后台启动的进程莫名消失 | 脱离会话 / `nohup` 被回收 | 用受管后台任务，别 `nohup &` |
| `mvn` 用错 JDK | 多版本共存，`java -version` 与实际编译 JDK 不一致 | 显式指定 JDK 路径 |
| `mvn package` 报「Unable to rename jar」 | jar 正被运行中的服务占用 | 先停服务再打包 |
| Git Bash 把 `/xxx` 改写成 `C:/Program Files/...` | MSYS 路径转换 | 参数前加 `//` 或双引号包裹 |
| 日志乱码 | CLI 输出 GBK | `iconv -f GBK -t UTF-8` |

## 四、质量保障体系（最值得照搬的部分）

### 三层验证，一层比一层接近真实

```
① mvn -o test          201 例   领域逻辑 / 状态机 / 越权 / Feign 契约
② 接口冒烟 .mjs         78 条    走 devServer 代理 = 前端真实请求路径
③ 浏览器走查 .mjs      199 条    CDP 驱动真 Chrome，收 console / 失败请求 / 破图 / 截图
```

一条命令收口：`node scripts/verify-e2e.mjs`（退出码 0 通过 / 1 断言失败 / 2 环境不满足）。

**关键设计**：冒烟脚本走的是 devServer 代理而不是直连服务。这一条让「网关路由配错」「代理路径剥错」这类问题在冒烟阶段就暴露——**绕过网关的测试，测不出网关的问题**。

### 本次新增：全页面诊断脚本

`diag-admin.mjs`：注入后台令牌 → 遍历 28 个平台页面 + 5 个商家页面 → 每页收集 console error / 未捕获异常 / 4xx-5xx 请求 / 白屏判定 / 截图。

**价值**：33 个页面 90 秒跑完，一次拿到全部页面级问题。人工点 33 页要半小时而且会漏。

### DDL 幂等纪律

三个迁移脚本，每个都跑两遍且 `exit=0` 才算通过。加列用 `information_schema` 判断后动态执行，不用裸 `ADD COLUMN`。

## 五、方法论（比代码更值钱）

1. **先让系统跑起来，再谈代码质量**。系统起不来时的代码审查全是猜测。这次开工第一件事就是把 10 个服务 + 3 端拉起来，之后所有判断都有实证。

2. **「单测全绿 + 端到端不通」是最高危信号**。它说明测试绕过了真实链路（网关、代理、鉴权、序列化）。遇到这种矛盾，先怀疑测试的路径，而不是怀疑功能。

3. **报错先分层定位，别急着改代码**。
   - `未登录或缺少访问令牌` = 网关文案（下游文案不同）
   - `Proxy error: Could not proxy request` = devServer 到后端不通（后端没起或正在重启）
   - 前端点击无反应且无网络请求 = 表单校验静默拦截，不是接口问题

4. **自动化诊断脚本 > 人工点页面**。脚本可重跑、可进 CI、输出结构化（JSON 报告），人工只能给一句「好像有点问题」。

5. **无数据时测不出契约错误**。分页字段名这类问题，空表时页面只是空着不报错。**造数据再验**是发现契约 bug 的必要条件。

6. **修完必沉淀**：现象（可 grep 的报错原文）+ 根因 + ❌/✅ 代码对照（从真实提交摘录）。只写道理不写代码的记录，三个月后自己都看不懂。

7. **并行开发靠「文件归属」隔离，不靠「约定」**。三个 agent 并行时用独立 git worktree + 按模块切工作包，抢文件是并行开发唯一的死穴。

# 售后闭环 需求

> 版本：v1.0　日期：2026-10-29　提出人：V4 规划（`docs/规划/商城-V4-售后与经营-规划.md` P0-1）
> 范围声明：本次只做 **P0-1 售后闭环**（R-01~R-05）。P0-2 经营看板、P1 超时关单/缩略图不在本次范围。

## 背景与目标

交易正向链路（下单→支付→发货→收货）已闭环，但**反向链路完全缺失**：

- `mall_refund` 表 18 个字段齐全，状态口径（1 待审核/2 已同意/3 已拒绝/4 已退款/5 已关闭）与类型（1 仅退款/2 退货退款）都已定义，但库里 0 行
- `MallRefundController` 只有代码生成器产出的通用 CRUD（page/save/update/delete），没有申请、没有审核、没有状态机
- C 端 H5 与 PC 都没有任何售后入口；后台 `mall_refund/index.vue` 是纯 CRUD 页，永远不会有「待审核」数据

**不做会怎样**：用户收到货不满意，系统里没有任何可走的路；演示时「交易闭环」是残缺的。

**目标**：让一笔订单能走完「申请售后 → 后台审核 → mock 退款 → 库存回补」全流程，双端可见、后台可操作、状态可追溯。

## 功能点

| 编号 | 功能点 | 优先级 | 说明 |
|---|---|---|---|
| F-01 | 售后凭证上传 | P0 | `POST /shop/upload`：会员上传商品/凭证图，返回 `url`。必须新开接口——实测会员 token 调 `/file/upload` 返回 `403 会员身份仅可访问商城前台接口` |
| F-02 | C 端申请售后 | P0 | 订单详情页入口。校验：本人订单、状态 30/40、无进行中售后、原因必填、金额=订单实付、凭证图 ≤6 张 |
| F-03 | 售后状态机 | P0 | `1→2/3`（审核）、`1/2→5`（用户撤销）、`2→4`（mock 退款）。全部条件 UPDATE，受影响行=0 即并发冲突 |
| F-04 | 后台审核 | P0 | 待审核列表 + 同意/拒绝 + 审核意见。仅 `status=1` 可操作，权限点 `mall_mall_refund:edit` |
| F-05 | mock 退款与库存回补 | P0 | 仅 `status=2` 可退款 → 置 4 + `refund_time`。**仅退款不回补库存；退货退款回补 stock 且 sales 回减** |
| F-06 | C 端售后查询 | P0 | 售后列表（按状态筛）+ 售后详情（状态、金额、审核意见、时间线）；订单列表/详情带售后角标 |
| F-07 | 事件写订单日志 | P0 | 售后 5 类事件写 `mall_order_log`（订单时间线可见），`operator_type` 1 会员 / 2 管理员 |
| F-08 | 双端页面 | P0 | H5 与 PC 都补齐：订单详情「申请售后 / 查看售后」、售后详情页、订单列表角标、申请表单 |

## 业务规则（口径写死，实现只允许一处）

1. **可申请条件**：`order.member_id = 当前会员` 且 `order.status ∈ {30 已发货, 40 已完成}` 且该订单**无进行中售后**（`status ∈ {1,2,4}` 视为进行中；`3 已拒绝` `5 已关闭` 允许重新申请）。
2. **金额**：本版只支持**全额退款**，`refund.amount = order.pay_amount`（含券后实付口径，运费为 0）。不接受前端传金额。
3. **类型**：`1 仅退款`（货未回/不要货，库存**不**回补）、`2 退货退款`（货已回，库存**回补**）。两种类型都直接由后台审核 → 退款，**不经真实物流回寄**（规划已声明简化）。
4. **库存回补时点**：在「置 4 已退款」这一步执行，且**只对 type=2**。回补必须与状态迁移同一事务，且靠条件 UPDATE 保证只执行一次（重复退款请求不应二次回补）。
5. **订单状态不变**：售后独立于 `mall_order.status`，已完成订单继续保持 40，不回退、不新增订单状态。
6. **退款单号**：`refund_no = "RF" + yyyyMMddHHmmss + 6 位随机`。`pay_order_no` **保留订单原支付单号**（对账用），mock 退款流水号写 `remark`（不覆盖原支付单号，与规划文案的差异在此说明）。
7. **一单一售后**：同订单可有多条历史售后记录（被拒绝/关闭后重新申请），但同一时刻至多一条进行中。

## 边界与异常

| 场景 | 期望行为 |
|---|---|
| 未登录调 C 端售后接口 | 401，前端跳登录 |
| 申请他人订单 | 403「无权操作该订单」 |
| 订单状态为 10/20/50/60 | 400「该订单当前状态不支持申请售后」 |
| 已有进行中售后 | 400「该订单已有进行中的售后申请」 |
| 原因为空 / 全是空格 | 400「请填写售后原因」 |
| 凭证图超过 6 张 | 400「最多上传 6 张凭证图」 |
| 上传非图片 / 超过 5MB | 400，提示类型或大小 |
| 审核非 `status=1` 的单 | 400「仅待审核的售后单可审核，请刷新后重试」 |
| 退款非 `status=2` 的单 | 400「仅已同意的售后单可退款，请刷新后重试」 |
| 重复点「同意退款」 | 条件 UPDATE 受影响行=0 → 400，不二次回补库存 |
| 用户撤销已同意/已退款的单 | 400「当前状态不支持撤销」 |
| 后台无 `mall_mall_refund:edit` 权限 | 403（PermissionChecker fail-closed，端点必须注册进 `MallRefundApiPerms`） |

## 验收标准

- [ ] F-01 会员 token 调 `POST /shop/upload` 传图片返回 200 + `url`，直链可访问；传 `.exe` 返回 400
- [ ] F-02 已完成订单可申请，`refund.amount` 等于订单 `payAmount`（与直接查库一致）
- [ ] F-02 待付款/已取消订单申请返回 400；申请他人订单返回 403
- [ ] F-03 合法迁移 `1→2→4`、`1→3`、`1→5`、`2→5` 全部成功；非法迁移（`3→4`、`4→5`）返回 400
- [ ] F-04 后台对 `status=1` 同意/拒绝成功，`status≠1` 返回 400
- [ ] F-05 仅退款（type=1）退款后 SKU `stock` 不变；退货退款（type=2）退款后 `stock` 增加、`sales` 减少
- [ ] F-05 重复调用退款接口第二次返回 400，且库存只回补一次
- [ ] F-06 H5 与 PC 订单列表能看到「售后中/已退款」角标，售后详情页状态文案与后端枚举一致
- [ ] F-07 申请/同意/拒绝/退款/撤销五类事件在订单详情时间线各出现一条，操作方正确（会员/管理员）
- [ ] F-08 双端功能一致：申请 → 查看 → 撤销三件事在 H5 与 PC 都能完成
- [ ] 三层验证：后端编译零错误、接口冒烟全绿、双端 CDP 走查 console 零 error 且有截图

## 待确认

- [x] 售后是否需要真实物流回寄？→ 否，规划已声明简化（同意即进待退款）
- [x] 是否支持部分退款？→ 否，本版仅全额退款，避免行级拆分
- [x] 退款对订单状态的影响？→ 不影响，`mall_order.status` 不回退
- [ ] 「仅退款」是否也要回补库存 → 已定为**不回补**（货已发出，未回库）。若业务认为仅退款等于订单作废需回补，需在 S6 前提出

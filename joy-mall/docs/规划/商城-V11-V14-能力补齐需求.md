# 商城（mall）V11–V14 能力补齐需求

> 文档性质：需求文档（差距补齐）
> 编制日期：2026-11-01
> 依据：V10 交付后对运行库与代码的全量盘点（52 张表 / 286 个接口 / 9 个微服务 / 68 个前端页面 / 127 例集成测试）
> 适用范围：V11 商家侧闭环、V12 交易真实化、V13 营销补面、V14 数据与体验

---

## 一、目标

当前系统交易主链路（下单 → 模拟支付 → 发货 → 收货 → 售后 → 分账）已闭环，但存在三类硬伤：

1. **不能对外营业**：支付是模拟的、运费恒为 0、物流只有手填单号、无发票、商家不能自助经营；
2. **能力有空转**：V8（秒杀/拼团/抽奖）与 V9（分销）共 100+ 接口、15 张表，三端零页面，用户不可见；
3. **运营缺抓手**：只有 8 个固定指标看板，无漏斗/留存/复购，无客服与触达通道。

本需求的目标是把「能跑的演示系统」补成「能开门营业、能持续运营的多商家平台」。

**验收总口径**：每个版本交付时，`mvn -o test` 全绿、`mall-cloud-fe-smoke.mjs` 与 `mall-cloud-ui-check.mjs` 零失败、DDL 脚本连跑两次幂等、`/health/aggregate` 全 UP。

- 支付：`ShopPayController` 为模拟支付；`mall_order` 有 `pay_type` / `pay_status` / `pay_order_no` 字段但无渠道实现。

## 四、P0 详细需求

### REQ-P0-01 真实支付

**现状**：`ShopPayController` 提供模拟支付，无第三方渠道，无支付流水与对账。

**功能需求**

1. 渠道接入：微信支付（Native 扫码 + JSAPI）与支付宝（电脑网站 + 手机网站），按端与运行环境路由；沙箱与生产配置分离。
2. 支付单：新增 `mall_payment`，一单一支付单，记录渠道、交易类型、金额、渠道交易号、状态（0 待支付 / 1 成功 / 2 失败 / 3 已退 / 4 部分退）。
3. 回调处理：验签 → 幂等（`pay_no` + `channel_trade_no` 唯一）→ 更新 `mall_order.pay_status` 与状态 20 → 触发下游（结算分账 / 分销佣金 / 消息）。
4. 竞态处理：支付回调与超时关单竞态时，**以回调为准**；已关闭订单收到成功回调 → 自动发起原路退款并写告警日志。
5. 退款原路：`mall_refund` 增加 `channel` / `channel_refund_no` / `refund_status`；退款失败可重试，重试幂等。
6. 对账：每日拉渠道账单与 `mall_payment` 逐笔比对，差异落 `mall_pay_reconcile`，支持人工处理标记。

**数据模型**

| 表 | 关键字段 |
|---|---|
| `mall_payment` | `pay_no`、`order_id`、`channel`(wxpay/alipay)、`trade_type`、`amount`、`status`、`channel_trade_no`(unique)、`notify_time`、`raw_notify`(JSON) |
| `mall_pay_reconcile` | `bill_date`、`pay_no`、`channel_trade_no`、`channel_amount`、`local_amount`、`diff_type`、`handle_status` |
| `mall_refund`（改） | + `channel`、`channel_refund_no`、`refund_status` |

**接口**

- `POST /shop/pay/prepay` 下单获取支付参数（返回二维码链接 / JSAPI 参数）
- `POST /shop/pay/notify/{channel}` 渠道回调（白名单，验签，返回渠道规定格式）
- `POST /shop/refund/notify/{channel}` 退款回调
- `GET /mall_payment/page`、`GET /mall_pay_reconcile/page` 后台查询与对账

**验收标准**

1. 沙箱环境：Native 扫码支付 → 回调 → 订单状态 20，`mall_payment.status=1`。
2. 同一回调重放 10 次，订单只推进一次，`mall_payment` 只有一行。
3. 订单超时关闭后再收到成功回调，自动发起退款，`mall_refund` 新增一条退款单且状态终态。
4. 退款成功后 `mall_refund.status=4` 且 `channel_refund_no` 非空；重复退款请求返回 400。
5. 单日 100 笔样本对账，差异为 0；人为构造 1 笔金额差异能被识别并落对账表。

### REQ-P0-02 运费模板

**现状**：`freight_amount` 字段存在但下单恒为 0。

**功能需求**

1. 模板管理：`mall_freight_template`（名称、计费方式 1 按件 / 2 按重量 / 3 满额包邮、是否默认）。
2. 规则明细：`mall_freight_rule`（模板、地区编码集合、首件数、首费、续件数、续费、满额免邮阈值），按地区精确匹配、无匹配回落默认模板。
3. 模板绑定：店铺级默认模板（`mall_merchant.freight_template_id`）+ 商品级覆盖（`mall_goods.freight_template_id`）。
4. 下单试算：按收货地址匹配地区规则计算；**跨店拆单按店铺分别计费**，各店铺运费计入各自订单。
5. C 端展示：确认页展示运费与包邮提示（"满 99 免运费，还差 X 元"）。

**接口**

- 后台：`/mall_freight_template/**`（CRUD + 规则维护 + 设为默认）
- C 端：`POST /shop/order/preview` 返回 `freightAmount`、`freightTip`、`freeShippingGap`

**验收标准**

1. 按件计费：首件 2 件 8 元、续件 1 件 3 元，买 5 件 = 8 + 3×3 = 17 元。
2. 按重量计费：首重 1kg 10 元、续重 0.5kg 4 元，2.8kg 向上取整 = 10 + 4×4 = 26 元。
3. 满额包邮：订单商品金额 ≥ 阈值时运费 0，且提示"已包邮"。
4. 跨店两店铺分别计算，两笔订单运费之和等于确认页展示值。
5. 收货地址为无规则地区 → 回落默认模板；无任何模板 → 运费 0 并打 WARN 日志。
6. `pay_amount = total_amount − discount_amount + freight_amount` 恒成立（单测断言）。

### REQ-P0-03 物流与发货单（含部分发货）

**现状**：`mall_order.express_company` / `express_no` 单组字符串，手填，无轨迹与批量能力。

**功能需求**

1. 发货单：`mall_delivery`（订单、快递公司、单号、发货商品明细快照、发货时间、状态），一单可多次发货。
2. 部分发货：按订单项数量发货，剩余数量仍为待发货；全部发完后订单才转 30 已发货。
3. 轨迹查询：接入快递查询服务（快递100 或快递鸟），结果缓存 30 分钟，C 端"查看物流"页展示节点。
4. 批量发货：Excel 模板导入（订单号 + 快递公司 + 单号），逐行校验，失败行输出原因报告。
5. 后台发货工作台：待发货列表、批量勾选发货、单号重复校验。

**接口**

- `POST /mall_delivery/ship` 单笔发货
- `POST /mall_delivery/batch` 批量导入
- `GET /shop/delivery/track/{orderId}` 轨迹查询（C 端）
- `GET /mall_delivery/page` 发货单台账

**验收标准**

1. 订单含 2 个商品项，各发 1 件 → 订单详情显示 2 个包裹，订单状态 30。
2. 只发其中 1 项 → 订单仍为 20，已发项显示"已发货"，未发项可继续发货。
3. 轨迹接口返回 ≥ 3 条节点时正确展示；无轨迹时展示"暂无物流信息"且页面无报错。
4. 批量导入 100 行，含 3 行错误（单号重复、订单状态不符、快递公司不存在），成功 97 行、错误报告 3 行。

### REQ-P0-04 发票

**现状**：无表、无接口、无入口。

**功能需求**

1. 开票申请：订单完成后可申请，抬头类型（1 个人 / 2 企业），企业必填税号；金额默认等于实付，不可修改。
2. 开票处理：后台开票队列，可上传电子发票文件（PDF/ofd），状态 0 待开 → 1 已开。
3. 红冲：已开票订单退款 → 提示红冲，红冲后状态 2 已红冲，原发票失效。
4. 查询：C 端"我的发票"列表可下载；后台可按订单号/会员/状态检索。

**数据模型**

`mall_invoice`：`invoice_no`、`order_id`、`member_id`、`title_type`、`title`、`tax_no`、`email`、`amount`、`status`、`file_url`、`red_flush_time`。

**验收标准**

1. 企业抬头未填税号 → 400；税号非 15–20 位 → 400。
2. 同一订单重复申请 → 400「该订单已申请开票」。
3. 后台开票上传 PDF 后 C 端可下载，文件可访问（HTTP 200）。
4. 已开票订单退款 → 状态转 2 并记录红冲时间。

### REQ-P0-05 商家独立后台与数据隔离

**现状**：商家由平台代管，无商家登录；`/mall_merchant/**` 全部为平台后台接口，无越权拦截。

**功能需求**

1. 商家账号：新增 `mall_merchant_user`（商家、账号、密码、角色、状态），与平台 `sys_user` 隔离；支持一个商家多账号。
2. 登录与令牌：`POST /merchant-auth/login`，令牌携带 `merchantId`，网关校验后注入请求上下文。
3. 数据隔离：MyBatis 拦截器对标注 `@MerchantScoped` 的 Mapper 自动追加 `merchant_id = 当前商家`；未标注的白名单放行。
4. 越权拦截：访问非本店资源（订单/商品/结算/提现）返回 403，并写入 `sys_oper_log`。
5. 商家自助能力：商品发布与编辑（限本店）、库存价格维护、订单发货、售后审核、结算单查看、提现申请、对账单导出（Excel）。
6. 商家端前端：独立工程 `fe/mall-merchant-web`（或复用 `mall-web` 按角色裁剪菜单，见待决策）。

**接口（新增 `/merchant-admin/**` 前缀，网关独立路由）**

- 商品：`GET/POST/PUT /merchant-admin/goods`、`PUT /merchant-admin/sku/stock`
- 订单：`GET /merchant-admin/order/page`、`POST /merchant-admin/order/{id}/deliver`
- 售后：`GET /merchant-admin/refund/page`、`POST /merchant-admin/refund/audit`
- 资金：`GET /merchant-admin/settlement/page`、`POST /merchant-admin/withdrawal/apply`
- 对账：`GET /merchant-admin/bill/export`

**验收标准**

1. 商家 A 登录后商品列表只返回 `merchant_id = A` 的数据；传入商家 B 的 `orderId` 返回 403。
2. 商家发品 → C 端列表立即可见（同店铺）；下架 → C 端 404。
3. 商家发货 → 订单转 30，平台后台同步可见同一状态。
4. 商家提现申请 500 元 → `account_balance` 立即减少 500，平台审核拒绝后余额恢复。
5. 平台管理员访问 `/merchant-admin/**` 返回 403（两侧令牌不通用）。

### REQ-P0-06 合规（协议 / 注销 / 信息导出）

**现状**：无用户协议、无隐私政策、无注销、无个人信息导出。

**功能需求**

1. 协议管理：`mall_agreement`（类型 1 用户协议 / 2 隐私政策、版本、内容、生效时间）；注册与登录页必须勾选并留痕（`mall_member_agreement_log`）。
2. 账号注销：申请 → 7 天冷静期（可撤销）→ 到期执行；订单与售后数据保留，`mall_member` 的 `phone` / `nickname` / `avatar` 匿名化。
3. 个人信息导出：会员可导出本人信息（JSON + CSV），含资料、地址、订单、优惠券，不含他人数据。
4. 脱敏：后台列表手机号中间四位掩码，敏感操作写入 `sys_oper_log`。

**验收标准**

1. 未勾选协议注册 → 400「请先阅读并同意用户协议」。
2. 注销申请后 7 天内登录，提示"注销冷静期，可撤销"；撤销后账号正常。
3. 冷静期到期执行后，`phone` 变为脱敏占位且无法登录；历史订单仍可被后台查询（`member_id` 保留）。
4. 导出文件含本人 3 条地址、1 笔订单，不含其他会员任何字段。

## 五、P1 详细需求

### REQ-P1-01 促销引擎

**现状**：只有优惠券（`mall_coupon` / `mall_coupon_record`），无满减、折扣、套装类活动。

**功能需求**

1. 活动模型 `mall_promotion`：类型（1 满减 / 2 满折 / 3 限时折扣 / 4 第二件半价 / 5 套装 / 6 加价购）、作用范围（全场 / 类目 / 商品 / 店铺）、规则 JSON、时间窗、优先级、是否可叠加。
2. 统一试算：`POST /shop/promotion/calculate`，固定顺序 **活动 → 券 → 积分抵扣**；活动之间按优先级与叠加配置计算。
3. 价格展示：商品卡与详情页展示活动价、原价划线、倒计时。
4. 命中留痕：`mall_promotion_hit` 记录活动 ID、订单、优惠金额，便于对账与投诉排查。

**验收标准**

1. 满 300 减 50 与 9 折同时命中，按"叠加"配置结果为 `(300 × 0.9) − 50`；按"互斥（最优）"配置结果为 `max(50, 30) = 50`（策略由配置决定，文档需明确）。
2. 活动过期后下单回落原价，`mall_promotion_hit` 不再新增。
3. 优惠金额大于应付时，`pay_amount` 取 0（`GREATEST` 保护），不为负。
4. 同参数试算与下单结果一致（100 次随机抽样断言）。

### REQ-P1-02 V8 / V9 前端页面

**现状**：秒杀、拼团、抽奖、分销共 100+ 接口、15 张表，`fe/` 下无任何页面。

**功能需求**

1. C 端（H5 + PC）：
   - 秒杀：活动列表（进行中/即将开始）、详情（倒计时、进度条、限购提示）、抢购
   - 拼团：团列表、开团/参团、团详情（成员、倒计时、成团状态）
   - 抽奖：转盘或盲盒交互、我的中奖记录、积分消耗提示
   - 分销：申请成为分销员、推广链接/海报、佣金明细、提现申请
2. 后台：秒杀活动管理、拼团活动管理、抽奖活动与奖品管理、分销员与佣金台账（复用生成器页面范式）。

**验收标准**

- UI 走查：4 个 C 端页面 + 4 个后台页零 console error、无空数据异常。
- 秒杀端到端：列表 → 抢购 → 预扣 → 建单 → 支付 → 后台可见；超限购返回明确提示。
- 分销端到端：申请 → 审核 → 生成推广链接 → 下级下单完成 → 佣金入账 → 提现申请。

### REQ-P1-03 会员等级与权益

**功能需求**：`mall_member_level`（等级、成长值阈值、折扣率、包邮次数、权益 JSON）；成长值来源（消费 1 元 = 1 点、签到、评价）；`mall_member` 增 `level_id`、`growth`；权益生效于下单试算（会员折扣、包邮卡）。

**验收标准**：成长值达阈值自动升级并写等级变更日志；会员折扣在详情页与下单试算一致；包邮卡用完回落到运费模板。

### REQ-P1-04 搜索增强

**功能需求**：商品标题/副标题/品牌/类目全文检索；拼音首字母与全拼；同义词（"手机"↔"移动电话"）；搜索联想（下拉 10 条）；热搜词（按搜索日志统计）；无结果时推荐同类热销。

**验收标准**：搜"手机"命中"悦集 X7 Pro 旗舰手机"；错字"手几"可纠错命中；`shouji` 拼音命中；P95 < 200ms（1000 商品量级）。

### REQ-P1-05 评价增强

**功能需求**：追评（原评价后 30 天内）、有用数、评价标签（物流快/包装好等）、晒单图片墙、按标签筛选。

**验收标准**：追评后详情页展示两条并标注"追评"；有用数幂等（同一会员重复点只计一次）。

### REQ-P1-06 售后扩展（换货 / 部分退款 / 平台介入）

**功能需求**

1. 换货：`mall_refund.type=3`，审核 → 买家寄回 → 商家收货确认 → 发出换货，库存**不立即回补**（收到退货后回补并扣减换出）。
2. 部分退款：按订单项选择退款金额，支持一单多次部分退款，累计不超过实付。
3. 平台介入：商家超时未处理（48 小时）可申请平台仲裁，仲裁结果可强制退款。

**验收标准**：换货流程走通且库存净变化为 0；部分退款累计超过实付返回 400；超时工单进入平台仲裁队列。

### REQ-P1-07 购物车营销

**功能需求**：凑单推荐（差 X 元可用券/满减）、降价提醒（收藏或加购商品降价通知）、失效商品专区（下架/售罄分开展示）。

**验收标准**：凑单提示金额计算准确；降价提醒只对本人商品触发一次。

### REQ-P1-08 客服工单

**功能需求**：会员提交工单（关联订单）、后台工单列表与回复、超时提醒、工单分类统计；后续可扩展 IM。

**验收标准**：工单提交后后台可见并可回复，会员端显示回复；超 24 小时未回复标记"待处理超时"。

### REQ-P1-09 消息触达

**功能需求**：短信（下单成功、发货、退款到账）+ 微信模板消息（已有 `openid`/`unionid` 基础）；统一消息模板管理；发送失败重试与降级到站内信。

**验收标准**：支付成功触发短信与站内信双通道；短信通道故障时站内信仍写入且日志标记降级。

## 九、明确不做 / 待决策

**不做**

- 自建支付通道、自研 IM 底层、直播推流自研、跨境多币种结算（V14 后另议）。
- 分库分表：当前数据量（订单 56、日志 211）远未到阈值，过早拆分只增加复杂度。

**待决策（落地前需与产品确认）**

1. 支付渠道：微信 + 支付宝直连，还是接聚合支付（Ping++ / 收钱吧）省对接成本？
2. 物流查询：快递100 还是快递鸟（费用与覆盖差异）？电子面单是否本期做？
3. 搜索：引入 Elasticsearch，还是 MySQL 全文索引 + 拼音词典过渡？
4. 商家端形态：独立工程 `mall-merchant-web`，还是复用 `mall-web` 按角色裁剪菜单？
5. 促销叠加策略：默认「互斥取最优」还是「可叠加」，由运营配置还是系统固定？
6. V8/V9 前端：先补 C 端还是先补后台管理页（影响运营能否先配活动）？

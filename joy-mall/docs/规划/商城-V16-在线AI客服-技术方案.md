# 商城（mall）V16 技术方案——在线 AI 客服

| 项 | 内容 |
| --- | --- |
| 版本 | V16（规划稿 v1，2026-11-02） |
| 定位 | C 端 7×24 首层自动应答 + 人机协作转人工闭环 |
| 新增服务 | `mall-ai`（8210） |
| 关联模块 | mall-support（工单）、mall-message（触达）、mall-order / mall-refund / mall-goods（内部契约） |

## 一、背景与目标

**现状痛点**：客服能力只有异步工单（`mall-support`），会员提问后需等待人工回复，售前商品咨询尤其低效——咨询等不到答复就流失。平台 48h 未处理虽会入仲裁队列，但那是兜底而非服务。

**目标**：

1. 售前（商品/优惠/政策咨询）与售中售后（订单/物流/进度查询）由 AI 首层自动应答，秒级响应
2. AI 无法解决的问题**确定性转人工**：自动生成带会话摘要的工单，进入现有工单处理流
3. **答案必须有依据**：检索或工具取证不到，就明说并转人工，不允许模型自由发挥编造政策

**衡量指标**：自助解决率（会话内关闭且未转人工比例）、转人工率、AI 首响时长（P95）、点踩率。

## 二、现状盘点（2026-11-02 实测）

| 依赖 | 现状 | 本方案如何用 |
| --- | --- | --- |
| mall-support 8208 | 工单 + 回复 + 48h 惰性超时仲裁，`category` 1-4，`first_reply_time` 等字段齐备 | 转人工 = 自动建工单（新增 category=AI 转接），复用 reply 通道人工回复 |
| mall-message 8209 | 短信/站内信 SPI + 模板 + 失败降级重试 | 「已转人工」「人工已回复」走站内信模板触达；SPI+降级的工程惯例直接复制到 LLM 层 |
| mall-order / mall-refund / mall-goods | 订单、物流轨迹、售后单、商品/优惠券均有 `/inner` 内部契约 | AI 工具取证全部复用现有 `/inner`，**不新建查询接口** |
| V14 搜索增强 | 词表 + 同义词 + 拼音 + 联想，MySQL 方案 | FAQ 召回复用同义词思路；ES 升级位预留 |

## 三、总体架构

```
C 端聊天窗(PC/H5) ──SSE──▶ 网关 ──▶ mall-ai (8210)
                                       │
              ┌────────────────────────┼──────────────────────────┐
              │ ChatOrchestrator 编排   │                          │
              │  意图识别 → 检索 → 工具取证 → LLM 生成 → 守护过滤    │
              └──┬───────────┬─────────┴───────────┬──────────────┘
                 │           │                     │
          LlmProvider SPI  KnowledgeRetriever   ToolGateway(白名单)
          openai兼容/本地/   FAQ+政策+商品        /inner 查订单/物流/
          mock（降级链）     (MySQL 起步)         售后/优惠券（只读）
                 │
                 └─▶ 兜底：FAQ 精确匹配 → 转人工(建工单) → 站内信触达
```

**核心组件**：

1. **ChatOrchestrator**：会话编排器。每条用户消息走「意图分类 → 证据收集 → 回答生成 → 输出守护」四步；意图分为闲聊 / 商品咨询 / 交易查询 / 政策咨询 / 投诉转人工五类。
2. **LlmProvider SPI**：与 `PayChannel`、消息渠道同一套工程惯例——接口 + 配置化实现 + 降级链。实现三个：`openai-compatible`（DeepSeek / 通义 / Kimi 等任选，生产主力）、`ollama`（本地 qwen，离线演示兜底）、`mock`（单测与 CI，不依赖外部）。任一 Provider 不可用自动降级到下一个，最终降级为 FAQ 精确匹配。
3. **KnowledgeRetriever**：FAQ（问题/答案/同义词/类目）+ 售后政策 + 商品信息的结构化检索。数据量小（预计 FAQ 数百条、商品数千），**MySQL 全文 + 同义词起步即可，不引入向量库**；表结构预留 `embedding` 列与 ES 接入位。
4. **ToolGateway**：工具白名单，**只读**。查订单/物流轨迹/售后进度/优惠券/商品详情五件套，全部代理现有 `/inner` 契约。AI 永远没有写权限（不能退款、不能改订单）。
5. **GatewayGuard**：输出守护——敏感词过滤、手机号等 PII 脱敏、幻觉闸门（无证据引用时强制走兜底话术）。

**一个关键技术决策**：不依赖模型的 function-calling 能力（本地小模型不稳定、云模型协议各异）。采用「**服务端确定性取数 + LLM 只做话术组织**」——意图识别和槽位提取（订单号/商品名）由规则 + 轻量分类完成，ToolGateway 拿到真实数据后，LLM 的职责仅是把数据组织成自然、有温度的回复。这样即使换最便宜的模型，数据正确性也不受影响。

## 四、数据模型（新增 5 表，`db/v16-ai-chat.sql`）

只列字段清单，不写 DDL：

| 表 | 关键字段 | 说明 |
| --- | --- | --- |
| `mall_chat_session` | member_id、channel(pc/h5)、status(0机器人/1已转人工/2已结束)、ticket_id、satisfaction、msg_count、last_active_time | 一次客服会话；转人工后双向关联工单 |
| `mall_chat_message` | session_id、role(user/ai/agent/system)、msg_type(text/order_card/goods_card/faq_suggest)、content、tool_trace(json)、tokens、latency_ms | tool_trace 记录每次工具取证的入参出参摘要，可审计 |
| `mall_faq` | question、answer、category、synonyms(json)、hit_count、status | 售前售后知识条目；命中计数支撑后台优化 |
| `mall_chat_feedback` | message_id、member_id、rating(up/down)、reason | 消息级点赞点踩，转人工触发的信号源之一 |
| `mall_ai_stat_daily` | 日期、会话数、消息数、意图分布、转人工数、token 消耗、成本估算 | 用量与成本看板数据源 |

## 五、接口设计

### C 端（网关路由 `/shop/ai-chat/**`，会员令牌；售前匿名走独立白名单 + 更严限流）

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| POST | `/shop/ai-chat/session` | 建会话（可带进入来源页上下文，如正在浏览的商品） |
| GET | `/shop/ai-chat/session/{id}/history` | 历史消息分页 |
| POST | `/shop/ai-chat/message` | 发消息；响应 `text/event-stream` 流式返回 AI 回答，事件含 `tool`（取证中）/`delta`（增量文本）/`card`（卡片）/`done`/`fallback` |
| POST | `/shop/ai-chat/feedback` | 消息点赞点踩 |
| POST | `/shop/ai-chat/transfer` | 主动转人工 → 建工单，返回 ticket_id |

### 后台（`/mall_chat/**`，平台令牌）

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/mall_chat/session/page` | 会话台账（状态/意图/满意度筛选） |
| GET | `/mall_chat/session/{id}` | 会话详情（含工具取证轨迹） |
| POST/PUT/DELETE | `/mall_chat/faq/**` | FAQ 增删改与启停 |
| GET | `/mall_chat/stat/overview` | 用量/成本/转人工率看板 |

### 内部（`/inner`，mall-ai 提供）

| 路径 | 说明 |
| --- | --- |
| `/inner/ai-chat/faq/search` | FAQ 检索（供 mock/兜底与其他服务复用） |

订单/物流/售后/优惠券取证**不新增接口**，mall-ai 作为 Feign 消费方直接调用现有 `/inner` 契约。

## 六、人机协作闭环

1. **触发转人工**（任一满足）：用户明说"转人工/投诉"；同会话连续 2 次兜底应答；点踩且再次追问；涉及退款金额争议等高风险意图（规则表配置）。
2. **转接动作**：`POST /transfer` → mall-ai 调 mall-support `/inner` 建工单：`category=AI 转接`、标题取会话主题、内容 = 会话摘要（LLM 生成，含已取证信息如订单状态）+ 工具取证 JSON；工单与会话互存 ID。
3. **人工回复**：坐席在现有工单页 reply（不新建 IM 坐席系统——MVP 阶段人工走异步工单，避免再造一套长连接基础设施）；mall-message 站内信触达会员「人工已回复」。
4. **会话状态机**：`机器人 → 已转人工 → 已结束`；转人工后 AI 停答，消息通道切到工单。

## 七、安全、合规与成本

| 项 | 方案 |
| --- | --- |
| Prompt 注入 | 系统提示与用户输入分角色隔离；用户输入永不拼接进系统指令；工具白名单只读，注入也无法产生写操作 |
| PII 与合规 | 输出侧手机号/地址脱敏；全部消息落库留痕（监管可回溯）；AI 回复明示"AI 客服"身份，不伪装人工 |
| 幻觉控制 | 回答必须引用检索证据或工具数据；证据置信不足 → 固定兜底话术 + 转人工引导，绝不生成政策承诺 |
| 成本控制 | 命中 FAQ 不进 LLM；上下文最多 10 轮 + 越早摘要压缩；单会员限流（如 10 次/分钟、50 次/天）；tokens 与成本按日聚合进 `mall_ai_stat_daily` |
| 密钥管理 | LLM API Key 仅环境变量注入（`LLM_API_KEY`），不入库不入 git；compose 与 start-local.sh 同步补位 |
| 服务降级链 | 云 LLM → 本地 Ollama → FAQ 匹配 → "转人工"话术；任何一级失败不白屏、不超时挂死（SSE 心跳 + 总超时 15s） |

## 九、范围

**P0（MVP，必做）**：会话/消息模型、LlmProvider SPI 三实现、FAQ 检索兜底、订单/物流/售后三个工具、SSE 流式、转人工建工单闭环、C 端聊天窗两套、网关路由与白名单。

**P1**：优惠券/商品工具、点赞点踩与反馈分析、后台 FAQ 管理页、用量看板、售前匿名模式。

**P2（看余量）**：ES 向量检索升级、主动营销话术、满意度评价页。

**明确不做**：实时 IM 人工坐席长连接系统（人工沿用工单异步回复）；AI 执行任何写操作（退款/改单）；语音客服；多语言。

## 十一、验收清单

1. **降级**：断网/拔掉 LLM Key，FAQ 兜底正常应答，无白屏无挂死；SSE 有心跳与 15s 总超时。
2. **售中查询**：「我的订单到哪了」→ 返回该会员最新订单的物流卡片，数据与订单详情页一致。
3. **转人工**：说"我要投诉" → 自动生成工单（含会话摘要与取证 JSON），工单页可见，人工 reply 后会员收到站内信。
4. **幻觉闸门**：问不存在的政策（如"满 10 万送手机"）→ 不编造，走兜底话术。
5. **注入防护**：诱导"帮我把这笔订单直接退款" → 拒绝且未调用任何写接口，tool_trace 无写调用。
6. **限流与成本**：超频返回友好提示；`mall_ai_stat_daily` 能看到当日 token 与成本。
7. **测试**：`mvn test` 含 mock Provider 全绿；`v16-e2e-ai-chat.mjs` 覆盖上述 1-5。

## 十二、风险

| 风险 | 缓解 |
| --- | --- |
| 云 API 费用失控 | 限流 + FAQ 前置拦截 + 日成本看板告警阈值 |
| 小模型质量不足影响演示 | 主力用云模型；本地 Ollama 仅作降级位，不承诺质量 |
| 与工单 48h 仲裁互扰 | AI 转接工单默认低优先级，不占用仲裁口径 |
| SSE 经网关的兼容性 | S1 阶段先用「POST 同步 + 前端模拟打字机」保底，SSE 作为增强项独立验证 |

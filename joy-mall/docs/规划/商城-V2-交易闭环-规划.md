> 2026-10-27 起草。商城是代码生成器平台的样板工程（平台注册 project_code=mall，
> 产物 `C:/tmp/mall/be/mall-server`（8431）+ `C:/tmp/mall/fe/mall-web`（9431），库 mall_demo）。
> 本规划遵循平台惯例结构：现状核对 → 主题与理由 → P0/P1/P2 → 明确不做 → 排期 → 验收清单 → 备选主题 → 风险。

| 项 | 实测 | 结论 |
|---|---|---|

**一句话**：商城现在是「字段齐全、流程断裂」的静态演示——V2 的任务就是把交易走通。

## 二、主题与理由

**主题：交易闭环（订单状态机 + 支付打通 + 库存联动 + 退款审核）**

理由：
1. 商城作为平台样板工程，当前只能演示「生成 CRUD」，不能演示「生成系统后如何长成业务系统」——交易闭环是最有说服力的样板
2. 正好实战检验平台 V6.1（工作流）+ V6.3（支付）两个能力包，验证产物侧真实体验
3. 顺手消化 2026-10-27 发现的三个平台缺陷（见「前置依赖」），一举两得

### P0：交易闭环主链路（必须）

| # | 功能 | 要点 | 验收 |
|---|---|---|---|
| F-01 | 开启支付能力包 | 平台把 mall 的 pay_enabled 置 1 → 重新 scaffold 增量写盘 → 验证不覆盖已手改文件（工作台/布局/字典） | 产物出现 pay_order 表 + /pay 端点 + 收银台页面，且手改文件完好 |
| F-02 | 订单支付打通 | 下单（后台代客下单或种子单）→ 收银台发起支付 → mock 渠道支付成功 → pay_order 与 mall_order.pay_status 双向联动 | 支付成功后订单列表状态变「已付款」，重复支付幂等（第二次数弹窗提示已完成） |
| F-03 | 订单业务动作 | 状态机：待支付→待发货→已发货→已完成 / 待支付可取消；发货填快递公司+单号；每步写 mall_order_log（操作人/时间/动作） | 订单详情页有「发货/收货/取消」按钮按状态显隐；非法状态迁移后端拒绝（如已完成单不可取消） |
| F-04 | 库存联动 | 支付成功扣 mall_sku.stock 并加 sales；取消/退款回补；扣减用条件 UPDATE（WHERE stock>=n）防超卖 | 并发下单同一 SKU 不超卖；库存不足下单报明确错误 |
| F-05 | 订单流转日志页 | order_log 已有表和页面，补「按订单号筛选」查询条件与中文动作标签（走字典） | 订单详情能看完整流转时间线 |

## 四、明确不做（本版本）

- **C 端商城（H5/小程序）**：V2 聚焦后台交易闭环，C 端是独立工程，留给 V3（可用 V6.5 移动端能力包起步）
- 秒杀/拼团/直播等营销玩法：等交易闭环稳定后再排
- 真实微信/支付宝对接：只用 mock 渠道跑通协议，真实渠道只差配置（密钥/回调域名），不在本版本验收
- 多商户/多店铺：单商户模型不变

## 六、验收清单

- [ ] mock 支付全链路：下单 → 收银台 → 支付 → 订单状态联动 → 幂等重放
- [ ] 订单状态机：合法迁移全通、非法迁移后端 400；每步有 mall_order_log
- [ ] 库存：支付扣减、取消回补、并发不超卖（JMeter 或多线程冒烟）
- [ ] 退款：申请 → 审核 → 通过回补库存 / 驳回恢复订单，全流程无手改数据库
- [ ] 平台侧：V6.6 前置项在 mall 重新生成场景下验证通过（字典/deleted 列/超管直通）
- [ ] mvn test（平台）全绿；商城产物编译零错；页面状态列全中文

## 七、备选主题（本次未选）

1. **营销能力包**（优惠券核销 + 秒杀 + 满减引擎）——依赖交易闭环先成立，故后置
2. **C 端 H5 商城**——演示价值高但工程量大，V6.5 移动端能力包可复用，留 V3
3. **多商户 B2B2C**——改表模型太大，不适合做小版本

## 八、风险

| 风险 | 应对 |

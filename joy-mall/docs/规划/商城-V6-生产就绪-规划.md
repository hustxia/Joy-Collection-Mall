# 商城（mall）V6 规划——生产就绪（测试重建 · 稳定性治理 · 可观测 · 容器化）

> 2026-10-31 起草。与《商城-V2-交易闭环-规划.md》《商城-V3-C端商城-规划.md》《商城-V4-售后与经营-规划.md》并列，前三版文档继续有效。
> V5 交付状态：后端由单体 `mall-server` 拆为 `mall-cloud` 六服务 + 网关 + 公共库，三端前端零改动接入，API 冒烟 51/51、浏览器走查 136/136 通过，已合并 master（`6205db9`）。
> **V6 定位：从「能拆」到「能上线」**——补回拆服务时丢掉的回归网，补上超时/熔断/鉴权/限流，加上 traceId 与指标，最后用一条 compose 命令拉起整套环境。

**一句话**：架构拆开了、链路通了、三端联调过了，但这套东西**没有测试网、没有超时兜底、没有网关防护、没有可观测、没有一条命令能起**——离「能上线」还差一层工程化。

## 二、主题与理由

**主题：生产就绪（Production Ready）——测得起来、扛得住、看得见、拉得起来**

理由：

1. **测试归零是当前最大风险**：V4 攒下的 1,393 行测试（交易全链路、售后状态机、超时关单、足迹、看板口径）随单体目录一起删掉了。V6 之后每改一处都是盲改，先补网再谈其他
2. **无超时是最容易踩的线上事故**：`/inner` 调用没有任何超时约束，goods 卡 30 秒，order 的线程就枯 30 秒，雪崩只差一个慢 SQL
3. **边界拆了但治理没跟上**：22 个 `/inner` 端点直接暴露在服务端口上，网关不做鉴权与限流，任何拿到会员 token 的人都能直接打 `8202/inner/sku/deduct` 扣库存
4. **演示说服力**：能一键 `docker compose up` 起全套 + 看到一个请求的 traceId 串起 6 个服务，比再加两个业务功能更能说明「这套架构真能上线」

## 五、明确不做（本版本）

- **注册中心 / 配置中心（Nacos、Eureka、Config Server）**：静态地址 + 环境变量仍可控；X-04 只做铺路，真接注册中心留 V7
- **分布式事务框架（Seata / TCC）**：继续「本地事务 + 显式补偿」，当前链路已验证够用
- **消息队列**：超时关单仍用轮询；延迟消息替代方案先记在 P2 后续评估
- **服务网格 / Kubernetes**：compose 满足演示与自测，不上 K8s
- **链路追踪后端（Jaeger / Zipkin）与告警**：只保证 traceId 贯穿 + 指标暴露，可视化后端按需再接
- **覆盖率目标（80% 红线）**：只覆盖交易与售后主链 + 契约面，不追数字
- **真实支付 / 物流 / 短信通知**
- **前端重构**：三端页面不动，只改构建产物进 nginx

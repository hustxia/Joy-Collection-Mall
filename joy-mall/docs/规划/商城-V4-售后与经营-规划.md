# 商城（mall）V4 规划——售后闭环与经营看板

> 2026-10-29 起草。与《商城-V2-交易闭环-规划.md》《商城-V3-C端商城-规划.md》并列，前两版文档继续有效。
> V3 交付状态：P0 全部 + P1 全部（发货/优惠券/交易核心测试），C 端 H5 与 PC 双端购物链路已跑通。
> **V4 定位：从「能下单」到「能运营」**——补上交易闭环唯一的缺口（售后），并把后台从纯 CRUD 变成能看数。

## 二、主题与理由

**主题：售后闭环 + 经营看板（让商城能退、能看数、能自愈）**

理由：

1. **售后是交易闭环的硬缺口**：用户收到货不满意，当前系统里没有任何入口。表已在、状态口径已定，只缺业务逻辑——投入产出比最高的一块
2. **看板是"运营可用"的门槛**：后台 13 个模块全是 CRUD，老板打开看不到今天卖了多少、哪款卖得好、退了多少。一个商城样板工程没有数据视角，演示说服力弱一半
3. **超时关单是"系统自愈"的底线**：现在 `status=10` 的订单会永久占住库存，越积越脏，且线上没有人工兜底
4. 三项都在 V3 的「明确不做」清单里被显式后置（退款 F-06 / 看板 F-07），属于**承诺兑现**而非临时起意

### P0-2：经营看板（2026-10-30 已交付）

> 实际落地与原设计有两点演进而非走样，已在交付时确认：
> 1. **接口从 `/summary?days=` 改为 `/overview?range=`**：`range ∈ {today,7d,30d}` 三档时间范围切换，比单一 `days=7` 更贴合运营日常（今日/近7天/近30天一键切）。**未做按天 GMV 趋势折线**——首页用时间范围切换 + 指标卡 + Top5 列表替代，复杂度更低、信息密度足够。
> 2. **后台不做根路由替换**（风险高、会动既有首页），改为在「其他」分组下新增「经营看板」菜单项（与 V4 售后的 `mall_refund` 注册方式一致，侧边栏从路由表自动推导）。

| #    | 功能     | 要点                                                                                                                                                         | 验收                           |
| ---- | ------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------- |
| D-01 | 看板接口   | `GET /mall_dashboard/overview?range=30d`（默认 30d，非法值回落 30d）：① GMV/订单数/客单价（pay_status=1 已支付，排除取消/关闭）② 退款金额 + 售后率（已退款单数 / 已支付订单数）③ Top5 商品（按成交量降序，≤5）④ 待处理项计数（待发货 status=20 / 待审核售后 status=1，全量 backlog）⑤ 新增会员数 | 数字与直接查库一致（单测 4 例 + 冒烟 43 断言）；空/异常数据不报错返回 0 |

## 五、明确不做（本版本）

- **真实物流回寄**：退货退款只做「同意→退款」，不接快递单回传、不做到货质检
- **部分退款 / 多商品分别退**：一单一次、全额或指定金额，不做行级拆分
- **真实支付渠道退款**：仍是 mock，`REFUND` 前缀单号，无第三方对账
- **财务对账 / 发票**：不上
- **评价体系**（商品评分、晒单）：不新建表，X-02 只留入口
- **消息通知**（短信/微信推送售后进度）：不做
- **合并 mall-shop 与 mall-pc**：双端继续并存，V4 只保证功能一致
- **对象存储 / CDN**：缩略图落本地磁盘，不引入 OSS

## 九、风险

| 风险                             | 影响         | 应对                                                             |
| ------------------------------ | ---------- | -------------------------------------------------------------- |
| 售后库存回补与订单取消回补重复执行              | 库存虚增       | 回补只在「退货退款审核通过」与「取消订单」两个互斥分支；回补前校验该售后单未回补过（`refund_time` 为空才回补） |
| 退款金额口径与订单实付不一致（券/运费）           | 对账对不上      | 统一 `refund.amount <= order.pay_amount`，且仅支持全额退款，P0 不开口子        |

| 定时任务与手工操作并发                    | 重复关单/重复回补  | 关单走条件 UPDATE（`WHERE status=10`），受影响行=0 即跳过；不加分布式锁（单实例部署）       |
| 缩略图生成阻塞首次请求                    | 首屏偶发慢      | 首次同步生成并落盘，之后命中缓存；生成失败降级返回原图而不是 500                             |

| `mall_order/index.vue` 已 934 行 | 加售后操作会更臃肿  | 本版不往该文件加逻辑（售后在独立页面），拆分留 X-01                                   |

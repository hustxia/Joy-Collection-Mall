## 1. P1-1 超时关单（交易自愈）

### 1.1 数据模型（S2）
- **新增列**：`ALTER TABLE mall_order ADD COLUMN close_time DATETIME DEFAULT NULL COMMENT '关闭时间（超时关单/手动关闭）';`（幂等：先 `SHOW COLUMNS` 判断是否存在再执行）
- 无新表。`mall_order_log` 复用。

### 1.2 功能点（S3）
1. **调度基础设施**：新建 `@Configuration` 类或在启动类加 `@EnableScheduling`。
2. **共享回补方法** `OrderStockBackfillService.backfill(List<Long> orderIds)`：
   ```sql
   UPDATE mall_sku s JOIN mall_order_item i ON s.id = i.sku_id
   SET s.stock = s.stock + i.quantity
   WHERE i.order_id IN (:ids) AND i.deleted = 0;
   ```
   比 `ShopOrderController.cancel` 的 N+1 循环更优；C 端 `cancel` 与定时关单共用，避免两处维护库存口径。
3. **定时关单** `OrderCloseScheduler`：
   - 每 5 分钟 `@Scheduled(cron = "${mall.scheduler.order-close.cron:0 */5 * * * *}")`
   - 扫 `SELECT id FROM mall_order WHERE status = 10 AND create_time < NOW() - INTERVAL ? MINUTE AND deleted = 0 LIMIT ?`（超时时长、批上限读配置）
   - 条件关单 `UPDATE mall_order SET status = 60, close_time = NOW() WHERE status = 10 AND id IN (:ids)`（受影响行=0 即跳过，**幂等**）
   - 回补库存（调共享方法）→ 写 `mall_order_log`（content="超时未支付自动关闭，库存已回补"，operator_type=3）
   - 整体 `@Transactional`，回补失败回滚
4. **并发安全**：与 C 端 `/shop/order/cancel`（也只锁 status=10）共享「条件 UPDATE 回补」模式——同一单被定时任务与手动取消同时命中时，条件 UPDATE 保证只有一个成功（affected=0 跳过），库存不双重回补。单实例部署不加分布式锁。

### 1.3 接口（S5）
- 无新增 C 端/后台接口（系统自愈）。仅配置项：
  ```yaml
  mall:
    scheduler:
      order-close:
        timeout-minutes: 30   # 超时时长
        cron: "0 */5 * * * *" # 扫描间隔
        batch-size: 200       # 单批上限
  ```

### 1.4 验收（S8 预估）
- 造 31 分钟前的 `status=10` 单 → 5 分钟内自动 60 + `close_time` 写入 + SKU 库存回补 + `mall_order_log` 有 `operator_type=3` 记录
- 单测（扩 `RefundFlowTest` 同类，固定时间偏移）：断言状态迁移 + 库存增量 + 日志条数
- 并发：手动 cancel 与定时扫到同一单，库存只回补一次

## 2. P1-2 图片性能（缩略图）

### 2.1 数据模型（S2）
- **无表变更**。缩略图落盘缓存目录 `./uploads/.thumbs/{w}/{name}` 与 classpath `static/img/.thumbs/{w}/{name}`（首次生成，之后命中）。

### 2.2 功能点（S3）
1. **统一缩略图端点** `GET /thumb?src=<相对路径>&w=300`（推荐，避免路径穿越）：
   - `ThumbService` 校验 `src` 必须以 `/uploads/` 或 `/img/` 开头（白名单防 `../` 穿越）
   - 读原图 → `ImageIO` 等比缩放到宽 `w`（高按比例）→ 质量 80 JPEG（PNG 原图转 JPEG 节省体积；JDK 自带，无新依赖）
   - 首次生成落盘缓存；之后命中缓存
   - **生成失败降级返回原图**（不 500，规划风险已提）
   - `AuthContextFilter.WHITE_LIST` 加 `/thumb`
2. **（备选）双路 ResourceHandler**：扩展 `FileWebConfig` 让 `/uploads/**` 支持 `?w=` 变体；`/img/**` 因是 classpath 默认映射需另起 Controller。统一 `/thumb` 端点更简单，选此方案。

### 2.3 接口（S5）
- `GET /thumb?src=/img/goods/x.png&w=300` → image/jpeg
- `GET /thumb?src=/uploads/2026/xx.jpg&w=300` → image/jpeg

### 2.4 前端改造（S7）
- H5/PC/后台**列表/卡片**商品图改引用 `/thumb?src=<原图>&w=300`；**详情页**保持原图（清晰）
- 改动点：`mall-shop` 商品卡片/列表、`mall-pc` 同上、`mall-web` 商品列表缩略图
- 后端 `mainImage` 字段语义不变（返回原图路径），前端按场景拼变体

### 2.5 验收（S8 预估）
- 列表页首屏图片总量从 6.5MB 降到 **< 800KB**（8 张 300×300 JPEG ≈ 480KB）
- 原图 `/img/goods/x.png`、`/uploads/**` 仍可访问；双端无破图
- 生成失败（损坏图）降级原图而非 500

## 4. P2-2 会员中心增强（X-02）

### 4.1 数据模型（S2）
- **新表** `mall_member_footprint`：
  ```sql
  CREATE TABLE mall_member_footprint (
    id          BIGINT PRIMARY KEY,
    member_id   BIGINT NOT NULL,
    goods_id    BIGINT NOT NULL,
    view_time   DATETIME NOT NULL,
    deleted     TINYINT DEFAULT 0
  );
  ```
  - 记录去重：同一会员同一商品 1 天内只保留最新 `view_time`（写时 `INSERT ... ON DUPLICATE KEY UPDATE view_time=NOW()`，唯一键 `(member_id, goods_id, DATE(view_time))` 或应用层判断）

## 7. 风险与对策（更新）

| 风险 | 影响 | 应对 |
| -- | --- | --- |
| 定时关单与手动取消并发 | 库存双重回补 | 共享「条件 UPDATE 回补」模式 + affected=0 跳过，天然幂等 |
| 长事务 | 批量关单锁表 | 单批上限 200（配置化），循环小事务而非一次大事务 |
| 缩略图首次生成阻塞请求 | 首屏偶发慢 | 同步生成落盘后命中缓存；失败降级原图；可后续改异步预热 |
| 缩略图路径穿越 | 读任意文件 | `/thumb` 校验 src 前缀白名单（`/uploads/`、`/img/`），拒绝 `../` |
| 关闭已付款订单退款口径 | 对账混乱 | 20→60 只回补库存不自动退款，退款走既有售后；改价 P2 不做 |
| 足迹表写入频率 | 性能/脏数据 | 同商品同日去重；逻辑删；列表带缩略图走 /thumb |
| 订单页拆分回归 | 既有订单功能坏 | 拆出的对话框组件复用既有接口，拆分前后接口零变化，UI 走查对照 |

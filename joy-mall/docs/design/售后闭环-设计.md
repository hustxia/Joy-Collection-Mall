## 一、表结构

### 1.1 现有表（无需 DDL）

`mall_refund` 已在库中存在（26 表之一），字段与需求完全对应，**本版不新增列、不改列语义**：

```sql
CREATE TABLE `mall_refund` (
  `id`              bigint       NOT NULL AUTO_INCREMENT COMMENT '主键',
  `refund_no`       varchar(32)  NOT NULL COMMENT '售后单号',
  `order_id`        bigint       NOT NULL COMMENT '订单ID 关联mall_order',
  `order_no`        varchar(32)  NOT NULL COMMENT '订单号',
  `member_id`       bigint       NOT NULL COMMENT '会员ID',
  `type`            tinyint      NOT NULL DEFAULT '1' COMMENT '售后类型:1仅退款2退货退款',
  `amount`          bigint       NOT NULL DEFAULT '0' COMMENT '退款金额(分)',
  `reason`          varchar(255) DEFAULT NULL COMMENT '申请原因',
  `evidence_images` varchar(2000) DEFAULT NULL COMMENT '凭证图URL JSON数组',
  `status`          tinyint      NOT NULL DEFAULT '1' COMMENT '状态:1待审核2已同意3已拒绝4已退款5已关闭',
  `audit_remark`    varchar(255) DEFAULT NULL COMMENT '审核意见',
  `refund_time`     datetime     DEFAULT NULL COMMENT '退款时间',
  `pay_order_no`    varchar(64)  DEFAULT NULL COMMENT '原支付单号 关联pay_order',
  `deleted`         tinyint      NOT NULL DEFAULT '0',
  `create_time`     datetime     NOT NULL DEFAULT CURRENT_TIMESTAMP,
  `update_time`     datetime     DEFAULT NULL ON UPDATE CURRENT_TIMESTAMP,
  `remark`          varchar(255) DEFAULT NULL,
  `create_by`       bigint       DEFAULT NULL,
  `update_by`       bigint       DEFAULT NULL,
  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_refund_no` (`refund_no`),
  KEY `idx_order` (`order_id`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='售后退款单';
```

**索引评估**：C 端列表按 `member_id + status` 过滤，表上没有 `idx_member`。当前 `mall_refund` **0 行**，数据量不足 1000 行前全表扫的成本可忽略，故**本版不加索引**（避免在没有收益的情况下改表结构）。若后续售后单过万，再补 `ADD KEY idx_member (member_id, id)`。

**字段语义补充（本版确定，写入注释不一致处以本文档为准）**：
- `pay_order_no`：**保留订单原支付单号**（`mall_order.pay_order_no`），用于对账。规划文案里的「REFUND 前缀退款流水号」改存 `remark`，不覆盖原支付单号。
- `refund_time` 只有 `status=4` 时有值，是判断「是否已执行退款」的唯一事实来源（库存回补的幂等依据）。
- `evidence_images`：JSON 数组字符串，如 `["/uploads/20261029/a.png"]`，与 `mall_goods.slider_images` 同语义。

## 二、功能设计

### 2.1 状态机（唯一实现 `MallRefundService`）

```
         ┌──────────┐  审核同意   ┌──────────┐  执行退款   ┌──────────┐
         │1 待审核  │───────────▶│2 已同意  │───────────▶│4 已退款  │
         └────┬─────┘            └────┬─────┘            └──────────┘
              │ 审核拒绝               │ 用户撤销
              ▼                        ▼
         ┌──────────┐            ┌──────────┐
         │3 已拒绝  │            │5 已关闭  │
         └──────────┘            └──────────┘
              ▲  用户撤销（1→5 同样可达）
```

| 迁移 | 触发方 | 前置 | 副作用 | 日志文案 |
|---|---|---|---|---|
| 1→2 | 后台审核同意 | status=1 | 写 `audit_remark` | 售后审核通过 |
| 1→3 | 后台审核拒绝 | status=1 | 写 `audit_remark` | 售后被拒绝：{备注} |
| 2→4 | 后台执行退款 | status=2 | `refund_time`、`remark`=退款流水号；**type=2 回补 stock 且 sales 回减** | 售后退款完成，金额 X 元 |
| 1→5 / 2→5 | 用户撤销 | status in (1,2) | — | 用户撤销售后 |

全部走条件 UPDATE：`UPDATE mall_refund SET status=? ... WHERE id=? AND status=? AND deleted=0`，受影响行 0 → 抛 400「请刷新后重试」。

### 2.3 后台列表页（改造 `fe/mall-web/src/views/mall_refund/index.vue`）

现有页面是生成器 CRUD 页（新增/编辑/删除），业务上无用。改造：**只读写业务所需**，保留生成器的表格骨架。

- 查询条件：售后单号、订单号、状态（下拉）、类型（下拉）
- 表格列：售后单号、订单号、会员（昵称+手机号）、类型、退款金额（元）、状态标签、申请时间、操作
- 操作：`待审核` → 审核；`已同意` → 确认退款；其余无操作
- 不提供「新增/删除」按钮（售后单只能由 C 端申请产生，避免脏数据）

## 三、接口设计

统一响应 `{code, msg, data}`，**错误也是 HTTP 200 + body.code**；`Long` 主键序列化为字符串。

### 3.1 C 端（前缀 `/shop`，会员 token）

| 接口 | 方法 | 路径 | 请求体 | 响应 |
|---|---|---|---|---|
| 凭证上传 | POST | `/shop/upload` | multipart `file` | `{url, name, size}` |
| 申请售后 | POST | `/shop/refund/apply` | `{orderId, type, reason, evidenceImages:[...]}` | `{refundId, refundNo, status}` |
| 我的售后分页 | GET | `/shop/refund/page` | query: `status?`, `pageNum`, `pageSize` | `Page<{id, refundNo, orderId, orderNo, type, amount, status, reason, createTime}>` |
| 售后详情 | GET | `/shop/refund/{id}` | — | `{refund, order:{orderNo,payAmount,status}, items:[], timeline:[{content,operator,operatorType,createTime}]}` |
| 撤销售后 | POST | `/shop/refund/close` | `{refundId}` | `null` |
| 可申请校验 | GET | `/shop/refund/order/{orderId}` | — | `{canApply, reason?, applyingStatus?}`（前端决定按钮显隐） |

订单接口增强（`ShopOrderController`）：

| 接口 | 变更 |
|---|---|
| GET `/shop/order/page` | 每条记录追加 `refundStatus`、`refundNo`（批量查 refund，按 orderId 取最新一条） |
| GET `/shop/order/{id}` | 返回体追加 `refund`（同结构，无则 null） |

### 3.2 后台（前缀 `/mall_refund`，sys token）

| 接口 | 方法 | 路径 | 请求体 | 响应 | 权限点 |
|---|---|---|---|---|---|
| 分页（改造） | POST | `/mall_refund/page` | `{pageNum,pageSize, refundNo?, orderNo?, status?, type?}` | `Page<MallRefundVO + memberNickname + memberPhone + refundTime>` | `mall_mall_refund:list` |
| 详情（复用） | GET | `/mall_refund/{id}` | — | `MallRefundVO` | `mall_mall_refund:list` |
| 审核（新增） | POST | `/mall_refund/audit` | `{id, agree:boolean, auditRemark?}` | `null` | `mall_mall_refund:edit` |
| 执行退款（新增） | POST | `/mall_refund/refund` | `{id}` | `{status, refundTime}` | `mall_mall_refund:edit` |

**必须同步的四处**（漏一处就是 403/404）：
1. `MallRefundApiPerms` 增加 `POST /mall_refund/audit`、`POST /mall_refund/refund` → `mall_mall_refund:edit`（fail-closed：不注册则写方法一律 403）
2. `AuthContextFilter.SHOP_ANON_LIST` **不加**（售后全部要会员 token，这是本版关键鉴权边界）
3. 前端 api 层：`fe/mall-shop/src/api/refund.js`、`fe/mall-pc/src/api/refund.js` 新增
4. devServer 代理已有 `/shop`，无需改

### 3.3 上传接口设计说明

会员 token 调 `/file/upload` 实测返回 `403 会员身份仅可访问商城前台接口`（`AuthContextFilter` 的会员身份隔离），因此**不能复用** `/file/upload`。

落盘逻辑抽到 `com.mall.common.file.FileStorageService`（**单一实现**），`FileController` 与新增的 `ShopUploadController` 都调用它：

```java
// 抽出的唯一实现，两处调用
FileRecord store(MultipartFile file, String createBy);  // 校验大小/扩展名 → 落盘 → 写 sys_file → 返回记录
```

`ShopUploadController` 只做三件事：限制仅图片扩展名（`jpg/jpeg/png/webp/gif`）、限制 5MB、返回 `{url,name,size}`（不暴露 `sys_file.id`，避免会员拿到后台文件 id）。
